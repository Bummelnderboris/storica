# FINDINGS — prompt/pipeline tuning notes

Observations gathered while running the pipeline agent-by-agent. Each is a candidate
tuning action, graded by leverage. Updated live as the run proceeds.

| # | Stage | Observation | Suggested action | Leverage |
|---|---|---|---|---|
| F1 | Phase 1 Topic | `subgenres` is collected by `TopicExplorationInput` but the `topic_exploration.yaml` template never references `{subgenres}` — "Justizdrama / Dorfgroteske" never reaches the model. | Add `{subgenres}` to the user prompt, or drop it from the input schema. | Low |
| F2 | Phase 1→2 threading | Verified: `raw_exploration` IS a required output field, so threading is sound. Downstream (Thesis) uses only `raw_exploration`; the other structured fields are barely consumed. | No fix needed for threading; see F3 re: wasted structured extraction. | Resolved |
| F3 | Planning agents (Phase 1, and same pattern likely in 2–5) | Each planning agent makes **TWO** LLM calls: (1) generate the prose analysis, then (2) a second "extraction" call to coerce it into the Pydantic schema (`_parse_exploration` in `explorer.py`). On `JSONDecodeError` it **silently falls back** to placeholder values ("See raw exploration", empty lists) — structured fields become useless while `raw_exploration` survives. **And** those structured fields are hardly used downstream. So the pipeline pays for an extra call per phase whose output mostly doesn't matter. | Either (a) drop the extraction call and thread the prose directly, or (b) use the provider's native structured-output/tool mode in ONE call instead of two, and treat a parse failure as an error rather than a silent placeholder. | **High** (hidden ~2× call cost + silent degradation) |
| F4 | Orchestration (my harness) | Sub-agents don't reliably call `Write` even when instructed (Phase 2 returned text, 0 tool calls). | In this capture I persist artifacts from the returned text myself. Not a product bug — a note for anyone scripting agents. | Low |

| F5 | Phase 5 Blueprint loop | Continuity between chapters is threaded as `prev_bp["raw_blueprint"][:800]` — the **first 800 characters** of the previous blueprint. In practice that's only the *Opening* section (hook + establishing details); the scene beats, emotional arc and closing image are cut off. So blueprint N barely "knows" how blueprint N-1 actually ended. | Thread a purpose-built 1–2 sentence summary of the prior chapter (or its Closing/Hook-Forward section) instead of a blind character-count slice. | **Medium-High** (weak inter-chapter continuity, compounds over a long book) |

| F6 | Phase 5 Blueprint (character drift) | The Ch2 blueprint recast **Berta** — the murder victim's *widow* — as Stettler's "wife or housekeeper." Root cause: during blueprinting the story bible is empty (`No entries yet.`), so no canonical character facts anchor the agent; even with characters in-prompt, a truncated/again-summarized context lets relationships drift. The bible that would catch this is only built later, in Phase 6. | Build (or pre-seed) the story bible from the Phase 3 character output BEFORE blueprinting, and thread it into every blueprint. This is the same root issue your notes flagged as the #1 fix (bible), seen from a new angle. | **High** (silent canon corruption that flows into prose) |

| F7 | Story bible (the #1 concern) — precise mechanism | `AgentStoryBible` keys characters/locations/objects in **dicts by name**, so they DO dedup — but only on exact string match. No normalization of name variants ⇒ "Stettler"/"Dr. Stettler"/"Konrad Stettler" become 3 characters. Timeline events are `list.append()`ed **with no dedup** (unbounded). `to_prompt_summary()` emits **all** characters every chapter (only timeline[-10:] and facts[:20] are windowed), so fragmentation inflates every downstream prose prompt. | (1) Normalize/merge character keys (canonical name, fuzzy match, or force the guardian to reuse existing keys by passing it the current name list). (2) Dedup timeline. (3) Cap characters shown in the prompt. This is your stated #1 fix, now with the exact code locations: `phase7_consistency/story_bible.py:111-155`. **CONFIRMED in Ch3:** when the guardian was passed the existing key list + a "reuse exactly" instruction, it reused all character keys with zero fragmentation — so fix (1) demonstrably works. Objects/locations still fragmented and timeline still grew unbounded, so (2)+(3) remain needed. | **High** (context bloat + cost, compounding per chapter) |

| F8 | Phase 6 critique gate (your #1 loop concern) | Ch1: an **honest** critic scored a real Opus draft **7.8 → PASS**, so the Reviser never ran — even though the critic itself listed real, fixable defects (explanatory-psychology line; thin "unease" beat). The 7.0 threshold sits below where a competent first draft lands, so every chapter pays for a critic call that structurally cannot trigger a revision. | Pick one: (a) raise the gate to ~8.5; (b) fire the reviser if **any single category** < 8, not just the average; (c) make the critique cheaper/skippable and only spend it where a revision could plausibly result. This directly reclaims cost with no quality loss. Confirms the field observation from the earlier 6-chapter run. | **High** (pure cost, zero effect as currently gated) |
| F9 | Phase 6 Writer (character drift, again) | The Writer recast **Rutz** — the village **priest** and Stettler's old friend — as an ordinary villager/creditor the dead man owed money ("der Rutz, dem der Tote Geld geschuldet hatte"). The Critic did NOT catch it, because its story bible was empty (Ch1) — so no canonical "Rutz = Pfarrer" fact existed to check against. Same root cause as F6/F7. | Seed the bible from Phase 3 characters before prose so both Writer and Critic have canonical roles. Watch whether the Consistency Guardian flags it now. | **High** (canon drift surviving the critic undetected) |

| F10 | Phase 6 Consistency Guardian (the cascade) | The guardian **crystallizes prose errors into canon**. With no prior bible to check against, it recorded the Writer's Rutz slip as fact ("Rutz: local creditor"), overwriting the Phase-3 truth (Rutz = priest/confessor). This wrong fact will now be threaded into Ch2/Ch3, where the blueprint still treats Rutz as the priest of the confession scene — a guaranteed canon collision. The guardian is a one-way ratchet: it *adds* what the prose says, it does not reconcile against the original character sheet. | Give the guardian the Phase-3 character canon as ground truth and have it flag prose that *contradicts* canon (not just extract new facts). Seeding the bible up front (F6/F7) prevents the error at the source. | **High** (single uncaught slip becomes permanent, self-propagating canon) |

| F8-UPDATE | Phase 6 critique gate — REVISED conclusion | Ch2 overturns the "loop never fires" story: with a **populated** bible the critic scored 5.8 → **REVISE**. So the loop is NOT uniformly dead weight — voice/quality nearly always pass on Opus drafts, and the ONE axis that can fail a draft is **Story Consistency**, which requires a populated (and correct) bible. Net: the revision loop's real-world function is mostly to **clean up the pipeline's own bible-drift**, not to improve prose. The earlier 6-chapter "never fired" observation was likely an artifact of a bible too empty/noisy to catch anything. | Keep the loop but recognize what it's for. If you fix the bible (F6/F7/F10), most consistency failures disappear and the loop genuinely can be cheapened/skipped (F8). If you DON'T fix the bible, the loop mostly fights fires the bible started. | **High** |
| F12 | Phase 6 reviser trap (self-repair AMPLIFIES corruption) — **PROVEN** | The reviser gets the critique but NOT the ground-truth character sheet. Told to "make it consistent," it "fixed" the 6 surface points and introduced WORSE corruptions: (1) renamed the victim Klara Vogel → "Anna Vogel, geb. Aebi"; (2) changed cause of death from fall → **poisoning** (contradicts Ch1's no-autopsy fall — breaks the central plot); (3) changed Stettler Amtsarzt → Amtsstatthalter; (4) split Rutz into a creditor + a separate unnamed priest; (5) moved Berta into Feuz's home as his domestic (widow→housekeeper, the F6 error reborn). Only the file-date fix was clean. A re-run critic would likely SCORE IT HIGHER (surface issues gone) while the book is far more broken. So the "quality" loop, on a corrupted canon, is a corruption AMPLIFIER. | Canon corrections must resolve to GROUND TRUTH (Phase 3 sheet), never the mutable running bible; thread the character sheet to BOTH critic and reviser; when bible/blueprint disagree, HALT for human/authoritative correction instead of letting the reviser guess. Evidence: `06_prose/ch02/4_revised.md`. | **Critical** (self-repair actively degrades coherence) |
| F11 | Phase 6 conflict "resolution" (canon corruption compounds) | When the Ch2 Reasoner hit the bible-vs-blueprint Rutz conflict, it did NOT treat the bible entry as a bug — it **fabricated a bridging fact** (Rutz is priest AND private creditor) and recommended saving that invented double-role to the bible. A contradiction thus becomes an *elaborated* false canon that is harder to detect downstream. (In the stock pipeline the reasoner isn't even asked to check conflicts, so it would blend silently.) | Contradictions between canon and a draft must raise a flag for correction, never be auto-reconciled by an agent. Pair with F10: give the guardian ground-truth canon and a "contradicts canon?" check. | **High** (self-elaborating canon corruption) |
